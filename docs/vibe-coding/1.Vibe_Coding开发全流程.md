# Vibe Coding 开发全流程：从 0 到项目上线

## 一、什么是 Vibe Coding

Vibe Coding 不只是让 AI 帮忙写代码，而是通过自然语言描述需求，让 AI
参与需求分析、产品设计、技术方案、编码、测试、代码审查、部署和后续迭代。

核心原则：

-   人负责目标、业务规则、技术决策和最终验收。
-   AI 负责辅助分析、制定计划、编写代码、执行测试和排查问题。
-   不要一次性让 AI 生成整个项目，而要按阶段、按任务逐步交付。
-   AI 的输出必须经过代码审查和实际验证。

本文以"个人任务管理系统"为例，技术栈采用 Go + Gin + GORM + MySQL +
Redis + Vue 3 + Docker。

项目功能包括：用户注册登录、任务创建修改删除、任务列表分页、任务状态管理、数据统计和容器化部署。

------------------------------------------------------------------------

## 二、完整开发流程总览

1.  需求分析：明确做什么、给谁用、解决什么问题。
2.  产品设计：确定功能模块、页面和用户操作流程。
3.  技术方案设计：确定技术栈、系统架构、数据库和 API。
4.  项目初始化：创建 Git 仓库、目录结构和开发环境。
5.  任务拆分：将大需求拆分为可独立实现和验证的小任务。
6.  代码开发：按模块逐步实现业务功能。
7.  测试验证：执行单元、集成、接口和端到端测试。
8.  代码审查：检查逻辑、安全、性能和可维护性。
9.  部署上线：构建镜像、部署服务、健康检查和回滚。
10. 监控迭代：监控日志、性能和错误，持续优化产品。

推荐工作循环：

**提出需求 → AI 分析并制定计划 → 人工确认 → AI 执行 → 测试验证 →
人工验收 → Git 提交 → 下一个任务。**

## 三、第一阶段：需求分析（Requirements）

### 3.1 明确项目目标

先回答四个问题：

  问题             示例
  ---------------- ------------------------------
  做什么？         个人任务管理系统
  给谁用？         个人用户
  解决什么问题？   管理日常工作和待办事项
  最终交付什么？   可注册、登录和管理任务的网站

### 3.2 梳理功能范围

将功能划分为优先级：

  优先级   含义                 示例
  -------- -------------------- -----------------------
  P0       核心功能，必须实现   注册、登录、任务 CRUD
  P1       重要功能             分页、搜索、状态统计
  P2       后续增强             邮件通知、数据导出

MVP（Minimum Viable
Product，最小可行产品）指优先交付最核心、可实际使用的版本，而不是第一版就实现所有设想。

例如： - 第一版：注册、登录、任务管理。 - 第二版：搜索、分页、统计。 -
第三版：提醒、导出、移动端适配。

### 3.3 需求分析 Prompt

``` text
你现在是一名资深产品经理和软件需求分析师。

我准备从零开发一个个人任务管理系统。

项目目标：
帮助用户管理日常待办任务，支持任务创建、
编辑、删除、查询和状态管理。

请先不要编写任何代码。

按以下步骤帮助我分析需求：
1. 明确项目目标和目标用户。
2. 分析核心业务场景。
3. 梳理功能模块。
4. 区分 P0、P1、P2 功能。
5. 梳理每个功能的详细业务规则。
6. 找出可能遗漏的需求和异常场景。
7. 对不明确的地方逐个向我提问。
8. 最后生成完整的 PRD 需求文档。

要求：
- 不要擅自补充重要业务规则。
- 不明确的需求先提问。
- 每个功能都要有明确的验收标准。
- 第一版优先实现 MVP。
```

### 3.4 PRD 应包含什么

PRD（Product Requirements
Document，产品需求文档）是后续设计和开发的依据，至少包含：

-   项目背景和目标。
-   目标用户和用户角色。
-   功能清单及优先级。
-   用户故事和业务流程。
-   详细业务规则。
-   异常场景和边界条件。
-   验收标准（Acceptance Criteria）。

示例：任务创建功能 - 用户必须登录才能创建任务。 - 任务标题不能为空。 -
任务描述允许为空。 - 每个任务必须关联一个用户。 -
新建任务默认状态为待处理。 - 用户不能修改其他用户的任务。

### 3.5 本阶段交付物

``` text
docs/
└── PRD.md
```

常见知识点：PRD、MVP、User Story（用户故事）、Acceptance
Criteria（验收标准）、需求优先级。

## 四、第二阶段：产品设计（UI/UX）

PRD 确定"做什么"，产品设计进一步确定"用户如何使用"。

### 4.1 页面规划

任务管理系统可以包含： - 登录页面：账号、密码和登录操作。 -
任务首页：任务统计、任务列表和快捷操作。 -
任务编辑页：标题、描述、截止时间和状态。 -
统计页面：任务数量、完成率和状态分布。

### 4.2 用户操作流程

登录流程示例：

``` text
打开系统
   ↓
输入账号密码
   ↓
前端校验参数
   ↓
请求登录接口
   ↓
后端校验账号密码
   ↓
生成 Token
   ↓
前端保存 Token
   ↓
进入任务首页
```

### 4.3 产品设计 Prompt

``` text
根据已经确认的 PRD.md，帮我设计任务管理系统的 UI/UX。

要求：
1. 设计登录页、任务首页、任务编辑页。
2. 采用现代 SaaS 管理后台风格。
3. 统一颜色、字体、间距和组件规范。
4. 考虑空数据、加载中、请求失败等状态。
5. 页面布局简洁，操作符合用户习惯。
6. 先输出设计方案，不要直接编写代码。
```

### 4.4 本阶段交付物

``` text
docs/
├── PRD.md
├── UI_DESIGN.md
└── USER_FLOW.md
```

常见知识点：UI、UX、Wireframe（线框图）、Prototype（原型）、Design
System（设计系统）。

## 五、第三阶段：技术方案设计

需求和产品流程明确后，再决定如何实现。AI
可以协助设计，但技术选型和架构决策需要开发者确认。

### 5.1 技术栈示例

  模块     技术             作用
  -------- ---------------- --------------------
  前端     Vue 3            页面展示和交互
  后端     Go + Gin         业务接口
  ORM      GORM             数据库访问
  数据库   MySQL            持久化存储
  缓存     Redis            缓存及其他辅助能力
  认证     JWT              用户身份认证
  部署     Docker Compose   容器化部署

### 5.2 系统架构

``` text
Vue 3 前端
    │ HTTP / REST API
    ▼
Go + Gin 后端
    ├── Router
    ├── Middleware
    ├── Handler
    ├── Service
    └── Repository
          ├── MySQL
          └── Redis
```

分层职责： - Router：注册路由。 -
Middleware：认证、日志、跨域等通用处理。 -
Handler：解析请求、参数校验、组织响应。 - Service：实现业务规则。 -
Repository：封装数据访问。 - Model：定义数据模型。

### 5.3 数据库设计示例

users 用户表：

  字段         说明
  ------------ --------------------
  id           用户 ID
  username     用户名
  password     密码哈希，不存明文
  created_at   创建时间

tasks 任务表：

  字段          说明
  ------------- ----------
  id            任务 ID
  user_id       所属用户
  title         任务标题
  description   任务描述
  status        任务状态
  due_at        截止时间
  created_at    创建时间

注意：任务查询、修改和删除时，后端必须根据当前登录用户进行数据权限校验，不能信任前端传入的
user_id。

### 5.4 API 设计示例

  方法     接口               作用
  -------- ------------------ ----------
  POST     /api/register      注册
  POST     /api/login         登录
  GET      /api/tasks         任务列表
  POST     /api/tasks         创建任务
  PUT      /api/tasks/:id     修改任务
  DELETE   /api/tasks/:id     删除任务
  GET      /api/tasks/stats   任务统计

### 5.5 技术方案 Prompt

``` text
请根据已经确认的 PRD.md 和 UI_DESIGN.md，
设计完整的后端技术方案。

技术栈：
Go + Gin + GORM + MySQL + Redis。

请完成：
1. 系统架构设计。
2. 项目目录结构设计。
3. 数据库表结构设计。
4. RESTful API 接口设计。
5. 请求和响应数据格式。
6. 用户认证和权限控制设计。
7. 错误处理和日志规范。
8. 配置管理方案。
9. 测试方案。
10. Docker 部署方案。

要求：
- 考虑可维护性和扩展性。
- 避免过度设计。
- 解释关键技术选型的原因。
- 不要开始编写业务代码。
- 不确定的地方先向我确认。
```

### 6.4 AGENTS.md

AGENTS.md 是项目级 AI 开发指导文件，用于告诉 AI
项目背景、技术栈、目录规范、测试命令和修改约束。

示例：

``` markdown
# 项目开发规范

## 技术栈
- Go
- Gin
- GORM
- MySQL
- Redis

## 开发规范
- 遵循分层架构。
- Handler 不直接操作数据库。
- 业务逻辑放在 Service。
- 数据库操作放在 Repository。
- 统一错误响应格式。
- 关键业务逻辑必须编写测试。

## 测试要求
- 修改代码后执行 go test ./...
- 不允许为了通过测试删除原有测试。
- 不允许未经确认修改数据库结构。

## 开发要求
- 修改前先阅读相关代码。
- 优先小范围修改。
- 不要擅自增加依赖。
- 完成后说明修改内容和测试结果。
```

AGENTS.md 是指导文档，不是代码，也不是 MCP 或 Skill。

## 七、第五阶段：任务拆分（Task Planning）

不要直接告诉
AI"把整个系统开发完成"。应该先将需求拆分为能够独立实现、独立测试的小任务。

  模块         任务
  ------------ --------------------------
  基础模块     Gin 启动、配置加载、日志
  数据库模块   MySQL 连接、模型、迁移
  用户模块     注册、登录、JWT
  任务模块     创建、修改、删除、查询
  统计模块     任务数量、完成率
  前端模块     登录、任务列表、编辑页面
  部署模块     Docker、Compose

### 任务拆分 Prompt

``` text
请阅读项目中的：
PRD.md
ARCHITECTURE.md
DATABASE.md
API.md

将项目拆分成可执行的开发任务。

要求：
1. 每个任务尽量独立。
2. 明确任务依赖关系。
3. 明确涉及的文件。
4. 给出具体实现步骤。
5. 给出完成标准。
6. 给出测试方式。
7. 标注 P0、P1、P2 优先级。

输出 TASKS.md。
暂时不要修改代码。
```

交付物：`docs/TASKS.md`。

### 8.2 单任务开发 Prompt

``` text
现在开始开发用户注册功能。

请先阅读：
- AGENTS.md
- docs/PRD.md
- docs/DATABASE.md
- docs/API.md

开发要求：
1. 实现用户注册接口。
2. 使用 Gin + GORM。
3. 密码使用 bcrypt 哈希存储。
4. 用户名不能重复。
5. 参数校验必须完善。

7. 编写单元测试。

执行要求：
- 先分析需要修改的文件。
- 先给出实现计划。
- 等我确认后再修改代码。
- 修改后执行测试。
- 最后说明修改了哪些文件、
  实现了什么功能、测试结果是什么。
```

### 8.3 常见 AI 编程概念

  名称                含义           使用场景
  ------------------- -------------- --------------------------
  Prompt              提示词         告诉 AI 要做什么
  Context             上下文         让 AI 理解项目背景
  Context Window      上下文窗口     模型一次能处理的信息范围
  Token               文本处理单位   影响上下文容量和模型消耗
  Agent               智能体         自主规划和执行多步骤任务
  Tool Calling        工具调用       AI 调用命令或外部工具
  Plan Mode           计划模式       先规划再执行
  Agent Mode          智能体模式     AI 自主执行多步骤任务
  Codebase Indexing   代码库索引     帮助 AI 检索和理解项目
  Diff                代码差异       检查 AI 修改了什么

### 8.4 编码阶段原则

1.  一个任务尽量只解决一个问题。
2.  修改前先阅读相关代码。
3.  先制定计划，再执行。
4.  修改后必须运行测试。
5.  完成一个稳定功能后进行 Git 提交。
6.  不要盲目接受 AI 的代码修改。

## 九、第七阶段：测试与问题修复

代码生成完成不代表功能完成。必须通过测试和人工验收。

### 9.1 测试类型

  类型       主要目的
  ---------- ------------------------------
  单元测试   测试独立函数和业务逻辑
  集成测试   测试数据库、Redis 等组件协作
  API 测试   测试 HTTP 接口
  E2E 测试   测试完整用户操作流程
  性能测试   测试并发量和响应时间
  安全测试   检查越权、注入等风险

### 9.2 测试流程

``` text
AI 完成代码
    ↓
运行单元测试
    ↓
运行集成测试
    ↓
启动前后端
    ↓
测试 API
    ↓
模拟真实用户操作
    ↓
发现问题
    ↓
AI 分析问题
    ↓
修复代码
    ↓
重新测试
```

### 9.3 问题排查 Prompt

``` text
当前任务管理系统的任务创建接口出现错误。

错误信息：
[粘贴完整报错]

相关代码：
[提供相关文件]

请你：
1. 分析错误原因。
2. 区分根本原因和表面现象。
3. 检查是否存在其他潜在问题。
4. 给出最小修改方案。
5. 修改代码。
6. 执行相关测试。
7. 说明修复结果。

不要通过删除测试或绕过错误的方式解决问题。
```

### 9.4 测试结果必须核实

-   是否真的执行了测试命令。
-   是否覆盖异常场景。
-   是否连接了真实测试数据库。
-   是否存在测试覆盖不到的业务问题。
-   是否引入新的回归问题。

AI 声称"测试通过"不等于测试确实通过，要检查实际命令和输出。

## 十、第八阶段：代码审查与安全检查

上线前应进行 Code Review。

### Code Review Prompt

``` text
请作为一名资深 Go 后端工程师，
对当前项目进行 Code Review。

重点检查：
1. 业务逻辑是否正确。
2. 是否存在 SQL 注入。
3. 是否存在越权访问。
4. 密码和敏感信息是否安全。
5. 是否存在并发安全问题。
6. 是否存在资源泄漏。
7. 数据库事务使用是否合理。
8. 是否存在 N+1 查询。
9. 是否存在性能问题。
10. 错误处理是否完善。
11. 日志是否包含敏感信息。
12. 测试是否覆盖关键场景。

要求：
先输出问题清单，按严重程度排序。
未经确认不要直接大范围修改代码。
```

重点概念：

-   Code Review：代码审查。
-   Security Audit：安全审计。
-   Static Analysis：静态代码分析。
-   Dependency Audit：依赖安全检查。
-   Regression Testing：回归测试。

-   有明确的回滚方案。

## 十三、Cursor、Claude Code、Codex 的分工

  开发环节     可选工具                       主要用途
  ------------ ------------------------------ --------------------
  需求分析     ChatGPT                        梳理需求、生成 PRD
  产品设计     ChatGPT + Cursor               设计方案、实现页面
  架构设计     ChatGPT + Claude Code          分析项目、设计架构
  项目初始化   Cursor / Codex                 创建项目和配置
  任务拆分     Claude Code / Codex            分析代码、规划任务
  代码开发     Cursor / Claude Code / Codex   编写和修改代码
  测试排查     Codex / Claude Code            运行测试、修复问题
  代码审查     Codex / Claude Code            检查代码质量
  部署上线     Codex / Claude Code            执行部署和排查

工具定位简述：

-   Cursor：IDE 集成度高，适合边看代码边开发。
-   Claude Code：终端 Agent，适合复杂代码库分析和多步骤开发。
-   Codex：适合委托编码任务、修改代码、执行测试和审查。

不必每个阶段都换工具。选一个主力工具，其他工具辅助即可。

## 十五、实际开发中的五条原则

1.  不要在需求不明确时让 AI 直接写代码。
2.  不要一次性让 AI 开发整个项目。
3.  不要不看 Diff 就接受 AI 修改。
4.  不要只相信 AI 说测试通过，要看实际执行结果。
5.  不要让 AI 自行决定所有架构和业务规则。

## 十七、最终建议

不要只学理论，直接用一个完整项目贯穿所有课程。

建议使用 Go + Gin + MySQL + Vue 3
开发任务管理系统，把已有的后端开发经验与 AI Agent 开发能力结合起来。

第一步先完成需求分析：通过 AI
提问明确目标用户、业务场景、功能边界和验收标准，最终产出
PRD.md。确认需求后，再进入 UI/UX、架构设计和编码阶段。

**记住：Vibe Coding 的核心不是让 AI 写得越多越好，而是让 AI
在明确目标、可控范围和可验证结果下持续交付。**
